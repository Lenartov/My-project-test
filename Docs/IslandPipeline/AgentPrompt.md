# Інструкція для іншого чату

Передай чату всю папку `Docs/IslandPipeline` або дай доступ до неї через файлові інструменти. Якщо передаєш лише цей текст, додай також README, BlenderAuthoring, TransferFormat та приклади JSON: без них не слід вгадувати контракт.

Нижче — готовий початковий запит. Після нього можна просто описувати бажаний вигляд острова.

---

Ти працюєш над модульними островами для Unity-проєкту з fragment reveal ефектом. Спілкуйся зі мною українською; code, identifiers та technical names пиши англійською.

Спочатку прочитай надані `README.md`, `BlenderAuthoring.md` та `TransferFormat.md` із папки `Docs/IslandPipeline`, а також каталог уже наявних моделей. Якщо документація або каталог недоступні, явно скажи про це; не вигадуй їхній вміст. Використовуй лише фактично доступні MCP-інструменти.

Я описуватиму бажаний вигляд, біом і наповнення острова. Твоя робота:

1. Знайти придатні бібліотечні assets і перевикористати їх; створювати тільки відсутні моделі або нові художні варіанти.
2. Зібрати редагований острів у Blender під одним root із платформою, декораціями та потрібними статичними маркерами. Звичайні повторення використовують спільні mesh data. Не об’єднувати весь острів в один Mesh.
3. Зберігати стабільні `asset_id`, `island_id`, `instance_id`, `parent_id` та `port_id` між правками. Не перетворювати rename чи переміщення на новий asset.
4. Задати footprint і docking ports відповідно до форми острова. Довгі сторони можуть мати кілька портів. Не нав’язувати однаковий розмір тайлів або кратність розмірів. Припускати Gap 0, якщо я не попросив інше.
5. Зберегти `.blend`. Експортувати нові/змінені моделі окремими FBX із залежностями, оновити каталог та передати повну композицію в JSON version 1. Незмінені моделі не експортувати окремими копіями для кожного острова.
6. Перетворити координати JSON за контрактом і перевірити, що FBX після Unity-імпорту матиме ті самі pivot/одиниці/осі. Не використовувати неперевірену перестановку Euler/quaternion компонентів.
7. Надати точні шляхи пакета, список нових/змінених/перевикористаних assets, розміри острова, порти й відомі проблеми. Відрізняти фактично збережені файли від плану.

Кінцевий Unity-результат має бути source prefab із редагованими екземплярами бібліотечних моделей і пов’язаний fragment prefab: готова геометрія, один синхронний `FragmentRevealGroup`, footprint та named ports. Baker уже має shared cache Mesh/FragmentMeshData за source Mesh asset та Cell Size: нова або змінена геометрія запікається в Editor, незмінена повторно використовується. Матеріали поки локальні для острова.

Не вважай exporter, JSON importer, logical registry чи shared material cache реалізованими лише через наявність цих документів. Якщо твоя роль — Blender-агент, підготуй пакет і звіт; не заявляй, що Unity prefab зібрано, якщо фактично цього не робив. Якщо ти Unity-агент, прочитай також `UnityImplementation.md` і перевір поточний код та актуальний статус перевірок shared mesh cache. Не запускай Unity, build, не додавай dependencies та не змінюй сторонні serialized assets без потрібного дозволу. Бібліотечні assets не видаляються при видаленні екземпляра.
